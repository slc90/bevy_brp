# 03 · 让点击、双击和拖动遵循真实 Picking 时序

## 目标

使自动点击、双击和普通控件拖动按实际 Picking 周期执行，并在结束或取消后释放活动责任。

## 范围

负责动作队列、定时等待、命中屏障、插值与终止；不涉及 OS 原生拖窗或窗口缩放。

## 预期产出

统一的跨帧手势排程、可靠的 generation 取消与 activity 收尾，以及时序回归。

## 与前后方案的关系

承接前两份方案的身份与基础动作；下一份方案对外固定这些行为的协议及使用说明。

本文件是顺序执行链中的第 3 份，具体位置见 [总览](00-overview.md)。需要查看完整设计时，使用 [总方案](../master-plan.md)。

## 基线与共同约束

版本：方案草案 1，2026-10-05。

核对基线：`slc90/bevy_brp@7eb70b5d24a19b8e7480b11bc1726af4e80cce6c`（本次读取时的 `main`）；配套消费方为 `slc90/bevy_widgetry@f32f5d0452cf8d63b6d506dc1060236e70367dd5`。仓库当前 workspace 版本为 `0.2.2`，依赖 Bevy `0.19.1`。仓库内容通过 GitHub 连接器读取；Bevy 行为另外核对了上游 `v0.19.1` 源码，而不是用浮动 `latest` 猜测 API。[B1] [U1] [U2]

这是一份待实施方案。本次没有修改仓库，没有运行 Rust 编译、测试、MCP 或桌面验收。下面的 `BrpPointerState`、`pointer_control`、动作队列和生命周期状态均是本方案提出的设计，不是声称仓库已经提供这些能力。

### 共同边界

目标是让 BRP 的普通鼠标操作只驱动 App 内的一只 `PointerId::Custom`，不移动系统光标，不伪造系统鼠标按键，不把 Widgetry 的业务状态直接改成测试希望看到的结果。正常输入路径是 `BRP → PointerInput → Bevy Picking → Pointer<T> → Widget`。物理鼠标仍由 Bevy 默认输入适配器产生 `PointerId::Mouse`，不被永久禁用或替换。[U1] [U2]

用户已限定 BRP 和真人不会同时操作。本方案不扩展为多操作者并发框架，但“没有同时动鼠标”不等于“没有残留 hover”。输入交接仍须结束旧动作、停用旧虚拟位置，并处理停在窗口里的物理 Mouse 位置。输入源识别留在 BRP；Widgetry 普通控件不识别 BRP 的 UUID，也不引入 BRP 生产依赖。

**Native Window move/resize 完整保持现状。** 不修改 Widgetry 的 `crates/window/src/title_bar/drag.rs`、`crates/window/src/title_bar/resize.rs` 及其现有原生操作、鼠标释放和系统 cursor 处理；不加 Custom Pointer 拒绝分支，也不添加程序化拖窗、缩放窗口或 OS 自动化替代实现。虚拟输入不支持这些原生拖拽区域，测试必须避开。保持代码不变不代表那里会自动拒绝 Custom Pointer：当前 observer 仍可能收到虚拟 Press 并发出原生拖拽请求。这是本次明确保留的边界，不得包装成已隔离或已支持的能力。[W3] [W4]

统一的是普通鼠标类 move、button、click、double-click、drag、scroll。keyboard、IME、截图、窗口标题、原生触控板 pinch/rotation/double-tap 是各自独立的能力，不把它们硬译成 PointerAction，也不借此次改动重写它们。Table 列宽拖动、ScrollArea 滚动条拖动属于普通控件交互，**不在 Native Window resize 的例外中**。不新增可见虚拟光标、overlay 或新的公共控件。

贯穿各部分的实现契约是：同一 App 的 BRP Pointer 身份稳定；普通输入只排队为 PointerInput，在既定 Picking 阶段消费；跨帧动作绑定 generation 与活动责任；取消不冒充正常 Release，清理完成前不允许新一轮输入穿过。取消通知补全只修框架生命周期，不直接改控件业务 state。官方 Hovered/DirectlyHovered 的 Custom 适配由消费方负责，不能为了样式退回伪造 Mouse。新 `pointer_control` 经现有 brp_execute 调用，status/release 及错误快照用于交接和诊断，不把请求接受等同于 UI 成功。

整个实施顺序固定为：本仓库小方案 01 → 02 → 03 → 04 → 05 → 06，再执行配套 Widgetry 小方案 01 → 02 → 03 → 04 → 05。Widgetry 前几个方案并不技术依赖本仓库发布，这个总顺序只是为了交接清楚；Widgetry 的最终接入才真正依赖本仓库可消费的固定版本。不得用浮动 `main` 或覆盖旧 tag 完成交接。

## 方案正文

### 已核实的分散路径

`click.rs` 有 timed release 和第二次 click 的调度；`button.rs` 有延迟释放；`drag.rs` 有自己的状态机、输入 writer 和光标更新。这些路径需要一起迁移，否则 move 不抢鼠标而 drag 仍抢，或者基础按键是 Custom 而 timer 又释放了 Mouse。[B4] [B7] [B8]

`BrpExtrasActivityGuard` 表示仍需 update 推进的真实工作。runtime 通过 Extras 活动变化和有界收尾预算续帧；这套责任不能在重构中丢掉，也不能把指针长期存在当成永久活动。[B9] [B10]

### 命中先于按下，按下先于释放

上游同一帧的命中取决于 pointer 最终位置，而 Release/Click 使用上一帧的 hover；多个坐标和点击全部塞进一帧会改变真正接收事件的实体。新队列必须按语义边界推进，而不是仅按 JSON 请求抵达顺序把所有消息一次写完。[U3]

普通 click 的顺序是建立目标位置并经过一次 Picking 命中，再发 Press，让按下状态被消费，之后按定时语义发 Release。位置已经稳定时不必机械重复一次定位，但必须有已消费的命中代数/阶段依据。首次 click、`duration_ms=0` 的定时按键、同帧连续请求也不能跳过这一保障。

一帧内不得把“移到 A、按下、移到 B、释放”当作已经忠实执行了一段跨目标动作。对依赖不同命中位置的队列项分隔 Picking 周期；不以“每个请求后睡固定毫秒”替代这一规则。返回当前请求的接受结果与动作真正完成是两件事。

### 点击与双击

保留各工具实际具有的字段及默认值：click 的默认按下时长、send_mouse_button 的 duration_ms、double_click 的 delay_ms；不声称每个工具都接受全部时间参数。双击由同一个 Custom pointer 上两次完整的 Press/Release 构成，不直接触发 `Pointer<Click>` 或把 count 写成 2。第二次按下与前一次的时间关系由真实定时与 Bevy `multi_click_interval` 决定；过大的 `delay_ms` 可能被应用识别成两次单击，这是应该记录的语义，不绕过引擎强制双击。[B7] [U3] [U5]

定时等待和阶段屏障分开：毫秒参数表达经过时间，阶段屏障保证输入经过处理。针对 App 暂停、低频更新、后台失焦等条件明确计时来源，并用真实经过时间推进自动化输入 timer，避免让虚拟游戏时间暂停把按键永远按住。不得把一轮按键 hold 的活动 guard 过早 drop；排队、按下、定时释放、消息消费和清理之间的责任交接必须唯一且幂等。

### 普通控件拖动

`drag_mouse` 保留 `start/end/frames/button/window`。起点 Move 与 Press 不再按当前实现那样先按再定位。其行为阶段为：起点命中建立、按下、插值移动、终点被消费、释放、动作收尾。`frames` 表达插值推进数量；起点准备与释放收尾是额外阶段，不能声称它等于整个操作的总 App update 次数。仍拒绝小于当前最低有效值的 frames。

插值覆盖终点一次，只有稳定的 start/end 和窗口目标，不在途中重新从真实 cursor 取数。按 `PointerInput` 生成正常 DragStart/Drag/DragEnd/DragDrop，不直接调用控件 observer。`frames=1`、start=end、拖出目标、终点在另一个控件、取消和目标窗口销毁都需有明确且可测试的终态。

仅替换普通控件拖动。即使使用同一个 `drag_mouse` 名称，也不表示可以驱动 OS 原生标题栏和边缘 resize；这一能力不新增，测试不把这些区域当目标。[W3] [W4]

### 取消、排队和活动责任

每项在途动作携带 generation、pointer、window 和实际拥有的按钮。普通动作使用 FIFO；同一时刻只允许一项自动 click/double-click/drag 操作拥有该指针，后续普通请求按队列等待，重复占有同一按钮、持有时跨窗口等冲突返回明确错误；定时持有期间允许的同窗口移动不等同于第二个自动手势。不能靠 Query 的实体迭代顺序决定最终操作顺序。

控制 release 是队列外的终止请求：失效旧 generation、取消尚未输出的动作、终止 timer、发 Cancel 并完成组件清理。窗口销毁同样走终止路径。动作结束或取消后所有对应 activity guard 只释放一次；旧操作不得再次写入消息。正常 Release 与 Cancel 的结果区分清楚，取消不能产生成功 Click、Drop 或重复业务通知。

不试图靠 stateless HTTP 的一次断线推断“整个用户自动化会话结束”。脚本在 finally 中显式释放；真人新的 Mouse 输入也会促成交接。没有活动任务且没有后续命令时，保留可继续 hover 的指针并不需要一直唤醒 App。状态查询不得把空闲 pointer 变成永久 busy；`busy=false` 也不能覆盖 last_error 所记录的失败。[B9] [B10]

### 此部分的验收

产出是共享队列驱动的三个跨帧操作和终止闭环。验收观察输入流、Picking 事件、Pressed/PointerPress、业务通知次数和 activity 数量，而不是只看最终 UI 值。尤其验证首次点击命中、多击 count、拖动最终位置、Cancel 时不触发点击、窗口销毁、旧 timer 失效，以及任务全部完成后按需更新恢复 idle。
