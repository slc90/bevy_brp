# 08 · 固化架构事实与 BRP 专属开发边界

**类型：规范建设方案。** 本文件属于待审改造方案；批准后按唯一执行顺序使用。

## 本项的共同边界

目标仓库是 `slc90/bevy_brp`，以方案 01 固定的当前 `main` 为起点，承接前序已完成的改造；方案 01 自身负责固定这个起点。不同步上游，不修改 widgetry，不安排用户学习仓库。Codex 只做完成本项目标需要的定位与实施，不顺手处理旁支目标。

先读本仓库现有 `AGENTS.md` 及命中规则。只定向读取当前方案点名的交接材料，不主动扫描历史 `plans/`；未实施的计划不能代替当前源码和事实文档。若任务与硬规则或必要前提冲突，停在受影响处并说明，不能自行放宽。

## 目标

把新架构变成后续施工能够遵守的稳定约束：当前实现在哪里看、依赖和可见性怎样判断、MCP 与 Bevy 侧的责任怎样区分，都有明确入口。

## 范围

以方案 07 已实施的结构和方案 02 的通用规则为基础，完善 `docs/architecture.md`、`rules/architecture.md` 以及确实需要的 BRP/MCP 边界规则。只保留有具体约束内容的规则文件，不为每个名词增加一份空规范。

## 目标状态

`docs/architecture.md` 描述实际 crate、模块角色、依赖方向、测试宿主与公共 API。架构事实变化时同项同步；普通源码调整或不影响这些事实的依赖版本变化，不要求机械改架构文档。

`rules/architecture.md` 约束如何新增边界、组织模块、选择可见性、处理生产与测试依赖。规则是判断标准，不是把当前目录树重复写一遍。生产 crate 是否存在由实际边界证明，不以“层数越多越好”或“crate 越少越好”为标准。

BRP/MCP 专属约束至少说清：MCP 服务层不承担 Bevy App 内部执行；BRP 客户端与传输职责有界；动态应用方法与静态 MCP 工具不是同一个注册面；结果与错误的实际语义不能仅因统一格式而丢失；runtime 与扩展插件的安装关系要有明确所有者。

应用日志与 MCP Server 自身日志在概念上分开。普通使用者应能得到应用开发需要的日志和错误；Server 自诊断是单独用途。这里确立边界，不提前决定方案 12 尚未确定的最终工具集合或启用机制。

`AGENTS.md` 路由到实际存在的文档和规则。`docs/` 是事实，`rules/` 是约束，`plans/` 是非默认的设计背景；当次指定方案仍作为任务输入。不得强制所有任务先把全部文档、历史计划和无关规范读完。

## 产出与验收

产出与当前代码一致的架构事实文档、BRP 专属规则和更新后的入口。按一个 MCP 修改任务、一个 Bevy 侧修改任务和一个纯文档任务检查路由是否适当、规则是否冲突、是否误带 Widget/Gallery 约束。

目标 MCP 接口尚未实施时，不把提议中的工具或参数写入当前 `docs/mcp.md`。若已建立该文档，只描述现状，等方案 13、14 同步更新。

## 与前后方案的关系

承接架构迁移，下一项建立可执行的行为回归基础。后续内部重整服从本项规则；接口重设计若确实需要改变规则，必须作为明确设计决定处理，不能在施工中悄悄放宽。

## 实施交接要求

未获批准的公共行为和消费方式保持不变。本仓库内直接受影响的位置一起处理；widgetry 等外部消费者只说明影响，不自动修改。不要覆盖用户已有工作，不自动提交、推送或发布。

按照当前规则执行必要验证。产生代码或工程行为改动时，由新的独立 reviewer 调用 `$code-review` 审查完整 working-tree change；施工 agent 修复 findings 后使用全新 reviewer 复审。没有独立审查能力时报告未完成，不能自审代替。纯 Markdown 且不影响工程行为的改动不强制执行代码审查。架构事实或公共 MCP 契约实际变化时同步对应 `docs/`。

完成后交接实际变化、验证结果、未测项和能否继续；只完成本项，不自动执行下一方案。已有问题、新增失败和环境限制分别报告。
