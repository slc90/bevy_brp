# 15 · 形成 MCP 消耗归因与有依据的优化决定

**类型：设计关口。** 本文件属于待审改造方案；批准后按唯一执行顺序使用。

## 本项的共同边界

目标仓库是 `slc90/bevy_brp`，以方案 01 固定的当前 `main` 为起点，承接前序已完成的改造；方案 01 自身负责固定这个起点。不同步上游，不修改 widgetry，不安排用户学习仓库。Codex 只做完成本项目标需要的定位与实施，不顺手处理旁支目标。

先读本仓库现有 `AGENTS.md` 及命中规则。只定向读取当前方案点名的交接材料，不主动扫描历史 `plans/`；未实施的计划不能代替当前源码和事实文档。若任务与硬规则或必要前提冲突，停在受影响处并说明，不能自行放宽。

## 目标

用实际数据确定哪一项优化值得做、要改变什么以及如何证明有效。既不回到学习阶段，也不默认把重复 schema、返回字段或发现调用当成已经确认的主要问题。

## 范围与对照

使用 `plans/refactor/01-baseline.md` 保存的原始样本和方案 14 已实施的公共契约。固定应用场景、状态、操作目标、客户端及必要环境；记录影响结果的版本和配置变化。

比较两种范围：原始基线到当前状态，反映整轮改造已造成的差异；当前状态到方案 16 的结果，反映后续专项优化的收益。两者不能混成同一个数字。接口已变化时按相同用户目标比较，写明不同调用序列，不能因为删除了验证动作就声称更高效。

## 要区分的观测量

工具枚举记录 tool 数量、description、input/output schema 与整个目录的原始字节量。它说明服务端输出了什么，不直接等于客户端每一轮实际送给模型的上下文。

实际工具交互记录 MCP 调用次数、参数与结果字节、错误与纠正次数、端到端耗时及任务是否正确完成。另行记录服务端到 Bevy 的 BRP/HTTP 请求数；一次 MCP 调用内部可能包含多个请求，这个计数不能冒充模型轮次。

取得真实客户端记录时再统计模型输入、缓存输入、输出 token 和可确认的模型轮次。取不到就报告“客户端实际 token 未测”，允许继续做有依据的字节或调用改进，但不得据此给出精确 token、价格或缓存收益结论。冷启动与重复会话条件也要分别记录，不假定工具定义只付一次或每轮都完整计费。

## 候选点与决定标准

候选点沿用讨论内容：工具目录和说明、重复或过度展开的 schema、返回 envelope 与重复参数、过量业务结果、type guide、错误详情、watch 输出、重复 discovery、大结果处理。检查实际 client/server 路径后再归因，不因为源码有某个机制就认定它必然产生对应模型成本。

优化以完成同一任务的正确性和总体交互效率为准。减少输出不能让 Agent 丢失作出正确决定必需的信息；减少一个工具也不能无代价地增加多轮探索。保留可解释的细节获取方式，不以静默截断、吞错或移除诊断依据换小数字。

每个建议给出观测证据、修改边界、预期作用、兼容影响和复测方法。没有证据的方向不进入施工清单。需要重新改变公共契约的建议必须显式说明；当前确认不足时停止该建议，不在性能阶段自动重新设计整套 API。

## 产出与确认关口

产出 `plans/refactor/15-efficiency-findings.md`，含可复现测量、实际结果、未测项目和明确的优化决定。可以得出“没有值得继续实施的改动”；这比凭感觉删信息更符合目标。

用户确认具体优化范围后，方案 16 才实施。如果无法取得原始样本，先说明不能证明整轮 before/after；可以保留当前状态作为专项对照，但不能伪造原始结果。

## 与前后方案的关系

承接新公共接口；下一项只实施这里确认过的优化。这个关口不要求必须减少多少 token，也不把一个特定客户端的表现概括成所有使用者的结果。

## 本项的执行方式

这是设计关口，Codex 的交付物是本文件指定的明确设计结论，不是生产代码变更。必要定位和不改变目标系统的验证可以进行；结论提交用户确认后停下。批准整份路线图不等于提前批准这里尚未形成的具体选择。
