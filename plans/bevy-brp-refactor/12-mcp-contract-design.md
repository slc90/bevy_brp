# 12 · 确定面向使用者的 MCP 契约

**类型：设计关口。** 本文件属于待审改造方案；批准后按唯一执行顺序使用。

## 本项的共同边界

目标仓库是 `slc90/bevy_brp`，以方案 01 固定的当前 `main` 为起点，承接前序已完成的改造；方案 01 自身负责固定这个起点。不同步上游，不修改 widgetry，不安排用户学习仓库。Codex 只做完成本项目标需要的定位与实施，不顺手处理旁支目标。

先读本仓库现有 `AGENTS.md` 及命中规则。只定向读取当前方案点名的交接材料，不主动扫描历史 `plans/`；未实施的计划不能代替当前源码和事实文档。若任务与硬规则或必要前提冲突，停在受影响处并说明，不能自行放宽。

## 目标

回答“Codex 使用这个 MCP 时应该看到什么、怎样调用、拿到什么结果”。方向是稳定、易用、必要的入口加按需发现的应用能力，不机械把每个 BRP 方法映射成原生 MCP 工具，也不为凑少量入口强行把一切塞进通用执行器。

## 范围与输入

使用当前已重整的实现、方案 01 的能力清单和对照样本。候选能力包括应用生命周期、world/resource/entity 操作、截图与输入、schema/type guide、应用动态方法、watch 和应用日志。只处理已讨论的能力边界，不扩展新产品功能。

## 必须给出的工具决定

逐项列出当前能力的目标去向：继续作为原生工具、与同类操作合并、通过动态发现加执行入口使用、归入内部自诊断，或在有依据与批准的情况下移除。每项写出原工具与目标入口、使用目的、参数、输出、失败语义和迁移影响。

最终原生工具数量由这张实际矩阵得出，不设数量指标。直接保留入口与动态执行之间，要判断参数约束、选择难度、发现调用和使用步骤，而不是只比较工具目录字节。

`brp_list_agent_tools` 所提供的应用目录与 Server 的原生 MCP tools 明确分开；`brp_execute` 的适用范围、动态方法的参数与结果约定、缺失方法和不支持调用方式的行为，都必须写成实际可验证的契约。不能假定动态目录条目会自动注册成原生工具。

watch、截图和输入有自己的执行与完成语义。合并入口不能破坏订阅清理、持续动作完成或错误可识别性。应用生命周期与本地日志工具也不应被强行伪装成普通 BRP 方法。

## 已定的自诊断边界

公共使用方式默认不暴露 MCP Server 自身诊断入口。当前明确的候选为 `brp_get_trace_log_path` 和 `brp_set_tracing_level`；其他自身日志访问也按用途纳入独立诊断面。

`brp_list_logs`、`brp_read_log`、`brp_delete_logs` 不能整组直接判成内部工具。要依据实际日志来源区分应用日志与 Server 自身日志。应用日志的必要能力继续服务使用者；是否共享底层实现不影响对外边界应清楚。

这里的“内部”描述用途，不是用户身份。外部使用者遇到 MCP 故障时仍可按文档显式启用自诊断；默认不暴露不等于永久删除。诊断面不属于普通公共 MCP 契约，但仍需可构建、可操作的排障路径。

具体使用现有 `mcp-debug` feature、其他构建安排还是其他明确机制，在本项给出一个选择及理由，不让方案 13 临时设计。普通构建和诊断构建分别枚举哪些工具、允许哪些调用，必须明确。

## 输入、结果与兼容结论

为目标接口确定参数 schema、默认值、必需字段、错误结构、业务结果和附加元数据的边界。不是预先决定“全删 envelope”或“全部保留”；每个字段要有明确用途。必要帮助信息应能被找到，不能用删说明替代设计。

变化涉及的旧工具名、参数或返回字段要有迁移说明。仅在真实消费者需要时保留范围明确的兼容入口；需要破坏性变化时用户先确认。默认承诺仍是保住未获批准移除的能力。

## 产出、确认与前后关系

产出 `plans/refactor/12-mcp-contract.md`：完整目标工具矩阵、参数和返回约定、代表性调用样例、动态机制、watch 等特殊语义、自诊断启用方式、应用日志边界、兼容决定及验收条件。

本项不修改实际 tool surface，也不把目标写成已实施的 `docs/mcp.md`。用户确认后，先进入方案 13 落实已定的自诊断分离，再由方案 14 实施其余公共契约。成本收益留到测量阶段，不在设计中宣称已经节省。

## 本项的执行方式

这是设计关口，Codex 的交付物是本文件指定的明确设计结论，不是生产代码变更。必要定位和不改变目标系统的验证可以进行；结论提交用户确认后停下。批准整份路线图不等于提前批准这里尚未形成的具体选择。
