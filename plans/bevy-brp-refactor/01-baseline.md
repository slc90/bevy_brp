# 01 · 固定当前 main 的改造基线

**类型：基线记录方案。** 本文件属于待审改造方案；批准后按唯一执行顺序使用。

## 本项的共同边界

目标仓库是 `slc90/bevy_brp`，以方案 01 固定的当前 `main` 为起点，承接前序已完成的改造；方案 01 自身负责固定这个起点。不同步上游，不修改 widgetry，不安排用户学习仓库。Codex 只做完成本项目标需要的定位与实施，不顺手处理旁支目标。

先读本仓库现有 `AGENTS.md` 及命中规则。只定向读取当前方案点名的交接材料，不主动扫描历史 `plans/`；未实施的计划不能代替当前源码和事实文档。若任务与硬规则或必要前提冲突，停在受影响处并说明，不能自行放宽。

## 目标

得到一个能重现、能比较、能区分原有问题与改造回归的起点。基线不是“先把整个仓库研究透”，也不要求把现有所有测试都修好才能开始。

## 范围

以开始实施时的 `slc90/bevy_brp:main` 为对象，记录提交、工作区状态、构建环境和入口。确认当前生产 crate、测试宿主、示例、实际使用的 feature，以及既有消费者使用的是路径、Git 引用还是其他方式。只检查本轮需要的直接关系，不追溯上游历史。

若本地存在用户未提交改动，记录其边界，不覆盖、不重置；不能把带有额外改动的运行结果冒充纯 `main` 基线。需要调整执行起点时取得明确决定。

## 应交付的基线

功能记录至少覆盖：MCP 的启动、工具枚举与调用；BRP 的发现、读取和修改；应用启动、状态和关闭；现有截图与输入能力；watch 的建立与结束；应用日志；MCP 自诊断；Bevy 侧 runtime 的请求推进。只记录实际存在的行为，不为凑表补新功能。

测试记录写明实际运行了什么、成功与失败是什么、失败是否已有、哪些因环境缺失未运行。现有针对边界情况的 fixture 和回归测试要能追溯用途，给后续删除提供依据。

MCP 对照样本保存固定的应用版本、场景、调用参数和响应。候选场景沿用讨论中的“启动应用、查找 UI entity、读取组件、修改组件、截图验证、关闭应用”，按当前确实可运行的能力固定下来。至少保存原始工具目录及一次可重放的代表性交互；MCP 调用次数、原始收发字节和成功情况分开记录。

可以取得客户端 token、缓存输入或模型轮次记录时一并保存；取得不到就标注缺失。不能用文件大小、服务端请求数或估算 token 冒充 Codex 实际消耗。这里只留 before 样本，不调查耗在哪里，也不实施优化。

## 产出与验收

产出 `plans/refactor/01-baseline.md`，记录起点、环境、功能清单、验证状态、样本位置和复现方式。原始大响应放在合适的本地测量资产位置，文档只引用必要摘要；日志或样本中的凭据、用户路径及其他敏感信息不直接纳入版本库。

完成标准是其他执行者能区分“已证实可用”“已知失败”“未测”。没有真实运行的能力只能标为未测，不能默认可用。若完全无法运行核心链路，明确这会阻断后续行为等价验收，先单独解决环境前提，不能在无验证依据下开始大规模重构。

## 与前后方案的关系

这是第一项，没有前序方案。之后进入通用 Agent 规范迁移。基线中的原始对照样本供最终验收及方案 15 使用；后续目录变化只更新复现指引，不覆盖旧样本或重写旧结果。

本项只记录现状与对照样本，不修复业务或调整 tool surface。取得结果后交接，未经用户明确授权不提交、推送或发布，也不自动推进下一项。
