# 14 · 实施新的公共 MCP 调用契约

**类型：实施方案。** 本文件属于待审改造方案；批准后按唯一执行顺序使用。

## 本项的共同边界

目标仓库是 `slc90/bevy_brp`，以方案 01 固定的当前 `main` 为起点，承接前序已完成的改造；方案 01 自身负责固定这个起点。不同步上游，不修改 widgetry，不安排用户学习仓库。Codex 只做完成本项目标需要的定位与实施，不顺手处理旁支目标。

先读本仓库现有 `AGENTS.md` 及命中规则。只定向读取当前方案点名的交接材料，不主动扫描历史 `plans/`；未实施的计划不能代替当前源码和事实文档。若任务与硬规则或必要前提冲突，停在受影响处并说明，不能自行放宽。

## 目标

让使用者实际看到方案 12 确定的公共 MCP 接口。不是只改工具名和 description，而是工具选择、参数、执行、结果、错误和说明都遵循同一份契约。

## 范围与输入

输入为用户确认的 `plans/refactor/12-mcp-contract.md` 以及方案 13 已完成的自诊断隔离。本项实施剩余公共工具、动态应用能力、类型指导与特殊调用语义，不重新发明工具分类，不顺手扩充未讨论的新能力。

## 完成后的接口

工具注册、调用分发、input schema、必要 output schema、help text 和实际参数解析保持一致。每个保留或合并的入口覆盖设计承诺的能力；通过动态机制提供的能力确实可以发现和调用，而不是删除旧工具后只留一句“可以用 execute”。

动态应用目录与 native MCP surface 各自承担约定职责。应用发布的目录用于提供其能力信息，Server 的通用入口按契约执行；不要在没有批准的情况下增加自动注册或额外发现层。

统一或简化返回结构时，业务结果、必要状态、错误原因和应用侧完成语义仍可判断。设计没有批准删除的字段或能力继续保留。type guide、watch、大结果落文件等机制只按已确认契约调整，不把成本阶段的猜想提前落实。

world/resource/entity、输入、截图和应用生命周期的行为用代表性操作验证。应用日志继续作为使用者能力，自诊断隔离不回退。旧工具或参数需要迁移的，提供准确映射与新样例；批准保留的兼容入口不得越过原定范围。

## 产出与验收

产出目标公共实现、实际可用的调用样例、契约测试和同步后的 `docs/mcp.md`、必要 README 内容。工具目录与文档能够相互核对，不残留只能在说明中找到、实际不可调用的入口。

与方案 01 的能力清单比较，逐项说明保留、迁移或批准移除的结果。重放同一用户目标时允许采用新契约对应的调用序列，但不能因为少做了任务而算通过。验证参数错误、找不到方法、失败结果和需要持续动作的路径，不只验证 happy path。

默认与诊断构建均检查正常能力，完成格式、编译、适用测试和独立 Code Review。成本表现暂不作为本项成功证明；本项成功意味着新契约真实成立。

## 未决前提与前后关系

若工具集合、参数、结果或兼容决定尚未在方案 12 获确认，停止对应实现。完成后进入方案 15，测量原始基线与当前新接口的实际使用消耗，不先宣称工具变少就一定更省。

## 实施交接要求

未获批准的公共行为和消费方式保持不变。本仓库内直接受影响的位置一起处理；widgetry 等外部消费者只说明影响，不自动修改。不要覆盖用户已有工作，不自动提交、推送或发布。

按照当前规则执行必要验证。产生代码或工程行为改动时，由新的独立 reviewer 调用 `$code-review` 审查完整 working-tree change；施工 agent 修复 findings 后使用全新 reviewer 复审。没有独立审查能力时报告未完成，不能自审代替。纯 Markdown 且不影响工程行为的改动不强制执行代码审查。架构事实或公共 MCP 契约实际变化时同步对应 `docs/`。

完成后交接实际变化、验证结果、未测项和能否继续；只完成本项，不自动执行下一方案。已有问题、新增失败和环境限制分别报告。
