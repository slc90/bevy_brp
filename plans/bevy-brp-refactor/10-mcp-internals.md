# 10 · 按新规范重整 MCP 内部实现

**类型：实施方案。** 本文件属于待审改造方案；批准后按唯一执行顺序使用。

## 本项的共同边界

目标仓库是 `slc90/bevy_brp`，以方案 01 固定的当前 `main` 为起点，承接前序已完成的改造；方案 01 自身负责固定这个起点。不同步上游，不修改 widgetry，不安排用户学习仓库。Codex 只做完成本项目标需要的定位与实施，不顺手处理旁支目标。

先读本仓库现有 `AGENTS.md` 及命中规则。只定向读取当前方案点名的交接材料，不主动扫描历史 `plans/`；未实施的计划不能代替当前源码和事实文档。若任务与硬规则或必要前提冲突，停在受影响处并说明，不能自行放宽。

## 目标

让 MCP 实现的职责、类型和控制流更直接，减少没有实际收益的自定义抽象。完成后不要求读懂一套额外“框架语言”才能修改普通工具，但也不为了减少类名破坏有效的类型边界。

## 范围与定位

使用方案 07 迁移后的真实路径。此前讨论中的定位线索包括 `mcp/src/mcp_service.rs`、`tool/`、`brp_tools/brp_client/`、`brp_type_guide/`、`app_tools/`、`watch_tools/`、`log_tools/` 以及 MCP 宏支持代码。它们不是要求重新恢复的目录名。

覆盖模块职责、可见性、命名、依赖方向、错误处理、日志、rustdoc、重复代码、无效分支和 lint 例外。被批准保留的宏在这里随调用方一起整理；已经在架构迁移中被替代的宏，不重建第二套实现。

## 重整后的样子

服务入口只管理 MCP 协议请求和分发；工具定义及注册有一个事实来源；参数处理、业务执行、结果映射和传输职责可分别定位。typed handler 与异构注册之间的有效类型边界可以保留，不能只因 `ToolFn`、`ToolDef` 或 `ErasedToolFn` 数量多就认定需要删除。

检查 `ToolName`、参数 schema builder、参数结构和帮助文本之间的重复来源。能减少重复维护时减少；但若涉及对外 schema 变化，记录交给方案 12，不能借“内部统一”静默改变客户端看到的契约。

输入处理保持既定语义：实际支持的 JSON 归一化、反序列化错误和参数默认值不能被整理掉。错误增强、type guide 与业务执行的归属更明确；不凭旧注释宣称存在自动纠错或重试，实际行为以实现和测试为准。尤其不能新增可能重复执行写操作的自动重试。

结果包装、字段放置、消息生成和大结果处理要有可解释的职责边界。可删掉不提供价值的间接层，但不能悄悄丢掉错误、截断有效结果或改变 watch 的生命周期。本项不以 token 节省为验收目标。

日志区分应用输出与 MCP 自身运行诊断，完善准确命名和内部归属；此处不修改公开工具集合。应用管理、watch 和诊断的边界行为保持，必要的日志或错误信息不因 lint 清理而消失。

## 产出与验收

产出符合新规范的 MCP 内部代码、必要测试和准确 rustdoc。每个保留的核心抽象能说明职责；删除的抽象有等价路径覆盖，没有并行存在的新旧框架。

用方案 09 的行为验证保护工具枚举、参数接受范围、结果与错误语义、watch、应用生命周期和日志。允许内部结构改变，不允许未获批准的外部能力变化。保持格式、编译、Clippy 和适用测试通过，完成独立 Code Review。架构事实变化必须有已批准依据并同步文档。

## 与前后方案的关系

承接回归验证基础，下一项重整 Bevy App 侧。两侧在这里按统一顺序处理，不虚构“Bevy 侧必须依赖 MCP 重构”的技术关系。公共 MCP 集合及成本问题留到方案 12 以后。

## 实施交接要求

未获批准的公共行为和消费方式保持不变。本仓库内直接受影响的位置一起处理；widgetry 等外部消费者只说明影响，不自动修改。不要覆盖用户已有工作，不自动提交、推送或发布。

按照当前规则执行必要验证。产生代码或工程行为改动时，由新的独立 reviewer 调用 `$code-review` 审查完整 working-tree change；施工 agent 修复 findings 后使用全新 reviewer 复审。没有独立审查能力时报告未完成，不能自审代替。纯 Markdown 且不影响工程行为的改动不强制执行代码审查。架构事实或公共 MCP 契约实际变化时同步对应 `docs/`。

完成后交接实际变化、验证结果、未测项和能否继续；只完成本项，不自动执行下一方案。已有问题、新增失败和环境限制分别报告。
