# 06 · 确定 workspace、crate 与公共 API 的目标架构

**类型：设计关口。** 本文件属于待审改造方案；批准后按唯一执行顺序使用。

## 本项的共同边界

目标仓库是 `slc90/bevy_brp`，以方案 01 固定的当前 `main` 为起点，承接前序已完成的改造；方案 01 自身负责固定这个起点。不同步上游，不修改 widgetry，不安排用户学习仓库。Codex 只做完成本项目标需要的定位与实施，不顺手处理旁支目标。

先读本仓库现有 `AGENTS.md` 及命中规则。只定向读取当前方案点名的交接材料，不主动扫描历史 `plans/`；未实施的计划不能代替当前源码和事实文档。若任务与硬规则或必要前提冲突，停在受影响处并说明，不能自行放宽。

## 目标

交付一份可以直接施工的目标架构。最终结论不能继续停留在“以后判断哪些 crate 值得存在”，也不能为了目录整齐机械保留现有四个 crate。

## 范围与依据

针对当前 `mcp`、`mcp_macros`、`extras`、`runtime` 及仍保留的测试宿主做必要定位，确认真实依赖、公共入口和直接消费者。只研究支撑目标架构的关系，不安排用户学习，不回看上游设计。

当前讨论中可用的职责线索是：MCP 服务运行在 Agent 一侧；extras 与 runtime 位于 Bevy App 一侧；runtime 组合扩展能力与自己的传输；宏用于 MCP 内部编译期支持。它们是设计依据的起点，不是必须维持的最终包结构。

## 必须形成的架构结论

生产 crate 放入 `crates/`。对每个 crate 明确保留、合并、替代或删除，列出目标路径、package 名、二进制名、职责、依赖方向和公共 API。名称与路径是两件事，不能为了移动目录无理由改动对外包名。

MCP 服务、内部工具框架、BRP 客户端和 HTTP 通信可以是清晰的模块边界，不要求每一层都独立成 crate。Bevy 侧的传输推进与扩展方法应有可解释的职责关系；只有真实的编译、依赖或消费边界才支持独立 crate。也不能因为只有一个消费者就自动认定某个 crate 无价值。

宏 crate 的决定必须连同替代成本一起给出。保留时说明它解决的重复和约束；删除时给出完整替代方式，不能只把宏源码搬到普通模块就宣告合并。runtime 与 extras 是否合并，同样要说明对插件安装、依赖与使用者入口的影响。

公共 API 仅覆盖外部消费需要。crate 内部默认私有；确需跨模块共享时使用最小足够可见性，必要时才用 `pub(crate)`；真正对外的边界才用 `pub`。不把所有实现都经 facade 再导出，也不把所有中间层都视为冗余。

测试宿主与示例要给出确定位置、Cargo 身份、测试入口和 fixture 依赖。虚拟 workspace 根下出现一个 `tests/` 目录，不是可执行测试入口已经成立的证据；方案必须说明它由哪个实际 package 或 harness 运行。保留现有独特回归行为。

直接消费者的影响必须入表：本仓库内部使用点怎样同步；外部 Git 或路径消费者是否需要改配置；已发布引用是否受影响；是否需要有期限、范围明确的兼容入口。不要默认“自己的仓库就可以随便 break”。widgetry 只读，不在本项修改。

## 产出与确认关口

产出 `plans/refactor/06-architecture-decision.md`，包含目标目录树、crate 职责与依赖表、公共入口、旧到新位置映射、测试宿主安排、直接影响及必要验证。需要保留兼容的地方写清原因，不默认长期维护所有旧接口。

本项只写目标设计，不把尚未实施的结构写成 `docs/architecture.md` 的当前事实。用户确认后才能进入方案 07。仍有关键去留、命名或消费决定未定时，不能视为可施工架构。

## 与前后方案的关系

承接已清理的工程现状，下一项按已确认架构迁移。它不决定 MCP 最终工具集合；内部架构可支持后续接口变化，但本轮不借架构设计先删公共工具。

## 本项的执行方式

这是设计关口，Codex 的交付物是本文件指定的明确设计结论，不是生产代码变更。必要定位和不改变目标系统的验证可以进行；结论提交用户确认后停下。批准整份路线图不等于提前批准这里尚未形成的具体选择。
