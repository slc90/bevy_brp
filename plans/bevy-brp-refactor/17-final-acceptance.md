# 17 · 完成工程验收、文档与消费入口收口

**类型：实施方案。** 本文件属于待审改造方案；批准后按唯一执行顺序使用。

## 本项的共同边界

目标仓库是 `slc90/bevy_brp`，以方案 01 固定的当前 `main` 为起点，承接前序已完成的改造；方案 01 自身负责固定这个起点。不同步上游，不修改 widgetry，不安排用户学习仓库。Codex 只做完成本项目标需要的定位与实施，不顺手处理旁支目标。

先读本仓库现有 `AGENTS.md` 及命中规则。只定向读取当前方案点名的交接材料，不主动扫描历史 `plans/`；未实施的计划不能代替当前源码和事实文档。若任务与硬规则或必要前提冲突，停在受影响处并说明，不能自行放宽。

## 目标

确认最终仓库就是方案承诺的独立工程，而不是若干局部修改的拼接。用户可以在改造完成后依据真实代码和当前文档单独学习，不需要重建这段聊天的全部决策。

## 范围

只处理本轮改造直接造成的缺口：全 workspace 验证、文档与入口一致性、实际消费者影响、已有 CI/验证流程适配、残余失效配置和已经证实不再需要的兼容代码。不是借最终收口开展另一轮架构改造。

## 最终应看到的仓库

README 描述现在的用途、接入和开发入口，不依赖上游历史叙事。`AGENTS.md` 是短入口；`rules/` 是适用的工程约束；`docs/architecture.md` 与 `docs/mcp.md` 只描述真实实现。`crates/` 中每个保留的 crate 有明确角色，测试宿主有真实运行入口，必要示例能演示当前公共用法。

Rust 版本、workspace metadata、共享依赖、格式和 lint 保持唯一基准；旧脚本和失效路径已经清掉。许可证与归属材料保留，不以根目录更简洁为目标抹去它们。

公共 MCP API 与自诊断面分开；正常构建默认不暴露自诊断，显式诊断方式仍可使用。应用日志正常可用，动态应用能力与原生工具的关系有准确说明。文档不得宣称未经测量的 token 节省比例。

## 完整验收

在已确认的工具链与支持环境执行最终格式、workspace 检查、Clippy、测试和构建。复核必要 feature 组合、普通与诊断构建，并重放代表性 MCP 到 Bevy 的真实链路。存在 GUI 或客户端环境缺口时列为未完成项，不用“其他测试全绿”掩盖。

逐项核对方案 01 的功能清单：保留的可验证，迁移的有新入口，删除的有明确批准。检查所有直接受影响的调用者、样例、测试和文档；外部消费者需要另行改动时明确列出，不能在本仓库宣称已经替它完成。

已有 CI 与本地验证口径一致。若没有 CI，先交付可重复的验证入口和剩余限制，不把未知的托管 runner、凭据或发布流程当成已经具备。引入新的 CI 基础设施需要单独明确决定，不为完成本项擅自扩展运维范围。

必要的最终独立审查针对尚未收口的完整改动及直接影响。发现有效问题就修复并复审。第二轮清理仅删除已证实失效、已有替代或批准到期的兼容代码，不用“最终清理”绕开接口确认。

## 产出与完成条件

交付最终源码、当前文档、工程配置、有效测试及简短验收记录。验收记录区分已通过、已知问题、未测项，并给出可复现入口与真实的效率对比。

有关键能力未验证、必要消费者影响未说明或独立审查未完成时，不能把整轮改造标为完成。仓库是否提交、打 tag、发布或更新外部引用由用户另行决定；本方案不自动执行这些动作。

## 与前后方案的关系

承接方案 16，是执行链最后一项。完成后停下，不附加学习阶段或新改造目标。用户之后单独学习新仓库，不属于本方案链。

## 实施交接要求

未获批准的公共行为和消费方式保持不变。本仓库内直接受影响的位置一起处理；widgetry 等外部消费者只说明影响，不自动修改。不要覆盖用户已有工作，不自动提交、推送或发布。

按照当前规则执行必要验证。产生代码或工程行为改动时，由新的独立 reviewer 调用 `$code-review` 审查完整 working-tree change；施工 agent 修复 findings 后使用全新 reviewer 复审。没有独立审查能力时报告未完成，不能自审代替。纯 Markdown 且不影响工程行为的改动不强制执行代码审查。架构事实或公共 MCP 契约实际变化时同步对应 `docs/`。

完成后交接实际变化、验证结果、未测项和能否继续；只完成本项，不自动执行下一方案。已有问题、新增失败和环境限制分别报告。
