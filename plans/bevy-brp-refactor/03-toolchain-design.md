# 03 · 确定可复现的 Rust 工程基准

**类型：设计关口。** 本文件属于待审改造方案；批准后按唯一执行顺序使用。

## 本项的共同边界

目标仓库是 `slc90/bevy_brp`，以方案 01 固定的当前 `main` 为起点，承接前序已完成的改造；方案 01 自身负责固定这个起点。不同步上游，不修改 widgetry，不安排用户学习仓库。Codex 只做完成本项目标需要的定位与实施，不顺手处理旁支目标。

先读本仓库现有 `AGENTS.md` 及命中规则。只定向读取当前方案点名的交接材料，不主动扫描历史 `plans/`；未实施的计划不能代替当前源码和事实文档。若任务与硬规则或必要前提冲突，停在受影响处并说明，不能自行放宽。

## 目标

形成一份能直接实施的工程基准，解决“到底统一到什么样”，而不是写一句升级工具链。本项只产出设计，不更新业务代码或依赖图。

## 范围

检查当前 Rust 版本需求、edition、Cargo resolver、格式化选项、workspace lint、Cargo 配置，以及 `deny.toml`、`mend.toml`、`taplo.toml` 等实际存在的辅助工具。widgetry 只作为约束思路的参考，不把它的版本和工具组合当成本仓库已验证答案。

## 必须形成的结论

Rust 版本使用明确的固定版本号，并列出所需组件与确实要支持的 target。当前对话没有给定这个版本，Codex 必须结合保留的依赖和工程选项提出具体选择及验证依据；不能擅自写浮动 `stable`、`nightly` 或“最新”。如确实需要特殊 channel，说明必要性并单独确认。

现状读取中使用的 edition 为 2024；没有实际需要时维持这一方向并集中声明。edition、Rust 工具链版本和 resolver 是不同配置，不能因为统一其中一个就顺手变更另外两个。保留 Bevy 0.19 方向，不把整套依赖大升级塞进此项。

统一 workspace package metadata 与共享依赖来源。设计列出哪些字段统一继承、哪些属于 crate 自己的名称、用途或 feature 需求。共同版本约束集中维护，但不要求所有 crate 因此启用同一组 feature，也不抹平作者、许可证或其他归属信息。

lint 要有可执行的统一标准：明确组级别、项目确需的例外及例外理由。不能通过全局放宽来掩盖后续尚未整治的代码。格式化配置与选择的工具链相容；仅因一个旧配置文件存在，不足以证明对应工具必须继续保留。

为每个辅助工具给出保留、删除或替代的结论。删除时说明它原本承担的检查是否不再需要，或由哪里接替；没有证据就不要先删。工程配置文件和文档命令之间只保留一套一致标准。

## 验证基准与产出

基准覆盖格式、workspace 检查、Clippy、测试和构建，并说明本地、GUI 和 CI 环境分别能验证什么。按保留的 feature 建立必要组合，不把 `--all-features` 当成对所有独立组合的替代。

产出 `plans/refactor/03-toolchain-decision.md`：具体版本与组件、metadata/依赖继承规则、配置去留、lint 口径、验证命令，以及会受影响的本仓库位置。

## 未决前提与确认关口

精确 Rust 版本尚未确定，这是本项要交付的决定，不由本总方案猜定。结论必须由用户确认后，方案 04 才能执行。若现有依赖无法满足候选版本，先呈现必要的工具链决定，不跨范围展开业务改造。

## 与前后方案的关系

承接方案 02 的通用规则；下一项只实施这里已经确认的工程决定。方案 01 的构建记录用于判断新旧差异，而不是要求维持原有配置错误。

## 本项的执行方式

这是设计关口，Codex 的交付物是本文件指定的明确设计结论，不是生产代码变更。必要定位和不改变目标系统的验证可以进行；结论提交用户确认后停下。批准整份路线图不等于提前批准这里尚未形成的具体选择。
