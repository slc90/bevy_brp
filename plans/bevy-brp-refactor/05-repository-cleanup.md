# 05 · 清理已经证实冗余的仓库资产

**类型：实施方案。** 本文件属于待审改造方案；批准后按唯一执行顺序使用。

## 本项的共同边界

目标仓库是 `slc90/bevy_brp`，以方案 01 固定的当前 `main` 为起点，承接前序已完成的改造；方案 01 自身负责固定这个起点。不同步上游，不修改 widgetry，不安排用户学习仓库。Codex 只做完成本项目标需要的定位与实施，不顺手处理旁支目标。

先读本仓库现有 `AGENTS.md` 及命中规则。只定向读取当前方案点名的交接材料，不主动扫描历史 `plans/`；未实施的计划不能代替当前源码和事实文档。若任务与硬规则或必要前提冲突，停在受影响处并说明，不能自行放宽。

## 目标

先减掉确定无用的历史包袱，让后面的架构设计面对真实需求，而不是一堆失效文件。这个阶段不是重新组织生产 crate，也不是依靠文件名决定删什么。

## 范围

检查旧文档、重复说明、无引用脚本、过期配置引用、不再使用的示例、历史兼容分支和显然不可达的代码。方案 04 已处理的工具配置不重复决定。本项只接收用途与影响都能确认的删除。

## 删除与保留的判断

每个删除对象要能回答：当前是否被构建、测试、文档或用户入口引用；是否保存了独特的行为说明或回归用例；删除是否改变仍在使用的接口、feature 或消费方式。后两者不能确认时保留并交给相应架构或接口阶段，不为了清理数量硬删。

`test-duplicate-*` 名字中有 duplicate，不等于内容无用。它可能在模拟重复包名、目标发现或其他边界；必须先确认现有测试如何使用它。独特测试行为需要继续覆盖，搬迁或替代由架构与测试阶段承担。不能用“以后再补测试”支持当前删除。

crate 的 README 与 CHANGELOG 也不按“根目录已经有一份”机械删除。纯重复叙述可以收拢；仍承担 crate 使用入口或版本行为记录的内容，要保留或迁移后再删除。所有留存链接和引用同步修正。

许可证、版权署名、第三方归属信息先保留。不再关心上游演化，不意味着这些文件成为历史垃圾。本轮不得以“独立化”为理由删除来源记录。

## 产出与验收

仓库只剩下有当前用途或明确保留理由的相关资产；对暂不能判断的对象给出短小的待定记录，不扩展成另一个全仓库研究项目。

删除相关的构建、测试或脚本引用后，验证原有使用入口没有断链。行为敏感的 dead code 或 feature 删除需要足够证据；一旦发现会改变公共行为，转入后续设计，不在这里越界。独立审查要特别检查误删回归资产、残留路径和 package metadata 引用。

## 与前后方案的关系

承接统一后的工程配置，下一项确定目标架构。本项不移动生产 crate、不重排依赖关系；这些动作集中在方案 07，避免清理与架构迁移混在一起。

## 实施交接要求

未获批准的公共行为和消费方式保持不变。本仓库内直接受影响的位置一起处理；widgetry 等外部消费者只说明影响，不自动修改。不要覆盖用户已有工作，不自动提交、推送或发布。

按照当前规则执行必要验证。产生代码或工程行为改动时，由新的独立 reviewer 调用 `$code-review` 审查完整 working-tree change；施工 agent 修复 findings 后使用全新 reviewer 复审。没有独立审查能力时报告未完成，不能自审代替。纯 Markdown 且不影响工程行为的改动不强制执行代码审查。架构事实或公共 MCP 契约实际变化时同步对应 `docs/`。

完成后交接实际变化、验证结果、未测项和能否继续；只完成本项，不自动执行下一方案。已有问题、新增失败和环境限制分别报告。
