# 任务边界规则

## 围绕明确目标工作

只修改完成当前目标所必需的代码和文件。每个 diff 都必须能够直接说明它为什么属于当前任务。

禁止顺手进行与目标无关的：

- 重构、bug 修复或命名调整；
- module、目录或 crate 重组；
- helper、抽象层或扩展点提取；
- 公共 API、MCP tool surface 或消费方式调整；
- 仅为了更统一、更现代或更美观而产生的改动。

发现旁支问题时可以在交接中指出，但不得混入当前修改。

## 必要修改自主完成

若不完成某项配套修改会使当前目标无法正确完成，可以自主实施，包括必要的局部重构、跨 crate 修改、测试、文档和配置同步。无需逐项请求确认，但不得借此扩大目标。

如果不做某项修改仍能完整完成当前目标，就不应修改。

## 保持公共边界

未经当前任务明确批准，不改变：

- 已公开的 Rust API；
- MCP tool 名称、参数、结果、annotation 或错误 contract；
- BRP method 与 transport 行为；
- Git tag、crate/package 名称或外部消费者的依赖方式。

若目标必然要求其中一项变化，应明确识别它并同步直接消费者、测试和事实文档；不得把意外变化包装成内部重构。

## 保护用户工作与外部消费者

本地已有修改属于用户。不得覆盖、重置或把它们混入当前结果；无法安全绕开时应停下说明。

外部消费者默认只读。除非用户明确把它纳入修改范围，不得修改其他仓库。

## 不保留猜测性实现

不得为未知未来需求提前增加 code、feature、dependency、配置、公共接口或 dead code。未来目标出现后再依据真实需求实现。
